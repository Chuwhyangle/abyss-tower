## 1. 背景

### 1.1 现状盘点（读数即代码）

| 事实 | 现状 | 出处 |
|---|---|---|
| 波次推进 | 线性 1..30 波、无节点图 | `MAX_WAVE = 30`（`public/js/shared/data/constants.js`）；推进权威在 `server/services/run-service.mjs` |
| 金币来源 | 5 类：击杀 / 清波 / 出售 / 周期性遗物 / 地图词缀；默认无利息 | `public/js/sim.js`、`public/js/shared/scoring.js` |
| 局内成长 | 无 XP / 等级系统 | — |
| 事件 | 每 5 波一次（`EVENT_WAVES = [5,10,15,20,25]`） | `public/js/shared/events.js` |
| 首领核心 | 每 5 波一次（`CORE_WAVES = [5,10,15,20,25]`） | `public/js/shared/boss-core.js` |

做爬塔需动的既有面：`server/services/run-service.mjs`、`server/routes/runs.mjs`、`server/services/run-rules.mjs`、
`public/js/shared/waves.js`、`public/js/app/combat.js`（+`public/js/app/run.js`）以及节点选择 UI。

### 1.2 核心设计

在现有 30 波难度阶梯上盖一层「**自选路线**」。节点图 seed 派生、**服务端权威**，只落两样状态：

- 选路决策（玩家在分叉处的选择）；
- 当前节点游标（走到第几层第几列）。

两样状态都塞进 `ruleset.tower.route`，**零 DB 迁移**（`ruleset` 已是 run 上的 JSON 字段，
沿用 `run-service.mjs` 现有读写路径即可）。

## 3. 节点图契约

| 契约项 | 冻结值 |
|---|---|
| 层数 | 30 层 DAG（覆盖既有 1..30 波难度阶梯） |
| 列数 | 每层 2~3 列 |
| 扇出 | ±1（每层最多分叉 1 列），稀疏格制造「路径承诺」 |
| 首领漏斗 | 5/10/15/20/25/30 层首领漏斗单列汇合 |
| 节点类型 | 打 / 事件 / 商人 / 精英（词缀强化+高稀有）/ 首领 / 宝藏 |
| seed 派生 | `${seed}:tower:*` 命名空间（独立随机流，**不触碰** `sim.js` / `events.js` 既有 RNG 调用顺序） |
| 状态落点 | `ruleset.tower.route`（选路决策 + 当前节点游标，零 DB 迁移） |
| 权威 | 服务端派生并校验候选，客户端不得自造 |

节点类型语义：

| 节点类型 | 内容 | 是否给遗物 | 备注 |
|---|---|---|---|
| 打 | 金币 + **唯一免费遗物** + 推进 | 是（唯一免费来源） | 常规战斗节点 |
| 事件 | 复用 `public/js/shared/events.js`，高风险高收益 | 否 | 不产遗物 |
| 商人 | 买遗物 / 升级 / 治疗 / maxHp / 刷新 / 卖遗物 | 金币购买 | 金币黑洞 |
| 精英 | 词缀强化 + 高稀有 | 视掉落 | 风险收益双高 |
| 首领 | 首领战斗 | 视掉落 | 10/20/30 漏斗层 |
| 宝藏 | 资源 / 上限类奖励 | 否 | 三资源分流的一环 |

## 4. 三类节点经济契约

### 4.1 三类节点

- **打**：金币 + **唯一免费遗物** + 推进。
- **事件**：复用 `public/js/shared/events.js`，高风险高收益，**不产遗物**。
- **商人**：金币黑洞——买遗物 / 升级 / 治疗 / maxHp / 刷新 / 卖遗物。

### 4.2 三闸（反「无脑选收益」）

1. **隐藏节点内容**：只露节点类型 + 词缀，不露具体收益；
2. **三资源分流**：遗物 / 上限 / 金币三条资源线分到不同节点，单一节点不能同时满足全部诉求；
3. **难度追击**：躲架（跳过战斗） = 遗物落后，难度随层追击。

### 4.3 经济口径

- **不新增金币来源**、**不引入局内 XP**（层数即等级，局外成长由天赋树承担）；
- 商人价目：普通遗物 **80 起** / 稀有 **160** / 史诗 **300**，按层上浮；
- `costMul` **不作用于商人**（防 −18% 双吃）；
- 刷新费随层涨：**25 + 6×波**。

### 4.4 8 条平衡红线（采纳经济视角）

| # | 红线 | 判据 |
|---|---|---|
| 1 | 遗物 12~15 次/局 | 单局获取遗物的总次数落在此区间 |
| 2 | 难度映射正确 | 见 §5（balance 实验定夺） |
| 3 | 商人买价 ≥60 | 商人最低单件买入价不得低于 60 |
| 4 | 治疗价 vs 卖血价防套利 | 买治疗与卖血之间不得形成无损套利 |
| 5 | 刷新费 25+6×波 | 刷新费随波次按此公式上涨 |
| 6 | 终局余金压回 2000~3000 | 终局剩余金币收敛到该区间 |
| 7 | `costMul` 作用域 | `costMul` 不作用于商人 |
| 8 | 囤币策略有出口 | 攒金币的行为有对应消费出口，不被死锁 |

## 5. 难度映射

关键待验证点（**balance 实验定夺**，落地前跑 `npm run balance`）：

| 方案 | 口径 | 风险 |
|---|---|---|
| A「楼层=波次」 | 每进一层难度 +1 波 | 最简单，但 15 场战斗 vs 30 波曲线可能太硬 |
| B「波次等价」 | 只战斗推进难度，事件/商人不推进 | 更贴合节点节奏，需额外映射规则 |

- 落地前必须 `npm run balance` 验证，并回写 `docs/BALANCE.md`；
- 映射定论未出前，实现任务**不得**自行拍板难度推进口径，以本节 balance 结论为准。

### 6.2 实现红线（架构视角，4 条）

1. **`MODES` 三处硬编码**：`public/js/shared/snapshot.js`、`public/js/shared/replay.js`、
   `server/services/leaderboard-service.mjs` 各维护一份 mode 白名单，加爬塔 mode 必须**三处同步**。
2. **`normalizeEventHistory` 会吞爬塔事件**：`public/js/shared/events.js` 的事件归一化需放行爬塔事件
   （否则快照/回放丢节点选择事件）。
3. **分享码要加 `route`（REPLAY_VERSION=3）**：`public/js/shared/replay.js` 的分享码需携带节点图选路，
   版本号从 2 升到 3。
4. **`sim.js` / `events.js` 确定性不得动**：新随机流用 `${seed}:tower:*` 命名空间，不得改变现有 RNG 调用顺序。

### 6.3 需重排的既有节奏

- 首领核心：现 5 次（`CORE_WAVES = [5,10,15,20,25]`）→ 重排为 **3 次（10/20/30）**；
- 契约卡 / 事件定时器：重排到节点。
